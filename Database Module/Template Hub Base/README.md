# Template Hub Base

`migrations/004_hub_admin.sql` gives managers (data role MANAGER, or active HR designation Manager) Template Hub admin rights; undo with `rollback/004_rollback.sql`.

`migrations/002_master_templates.sql` records the master Word file uploaded in Settings for each generated document, keeping every earlier upload.

Database for the CRM's **Template Hub** tab (`Template Module` folder, formerly Document Generator), in the CRM Supabase project.

Its existing tables and storage keep their names, because live data and other code use them. Their SQL is in `Template Module/database` (`quotation_templates`, its access and history). New Template Hub SQL goes in `migrations/` here.

### Signing (011): where signed files go and what counts as a change

The company comes from the row: Ardentax for `ardentax_documents` and for `hub_documents` whose `library_template` starts with `Ardentax`, AB Capital otherwise. Signed files sit beside the unsigned ones, under the document's own prefix plus `/signed/`, so the bucket's existing read rules cover them; `doc_sign_record` refuses any other path, and needs both the Word and the PDF file.

| Table | Bucket | Unsigned files today | Signed prefix | Change stamp (`doc_changed_at`) | Content columns (`content_changed_at` trigger) |
|---|---|---|---|---|---|
| `hub_documents` | `hub-documents` | `<department>/<id>/<uuid>.docx` or `.pdf` (`hubApi.saveFile`, `accountingApi.uploadDoc`, `proposalApi.uploadProposalFile`); Ardentax library rows under `Ardentax Documents/<id>/` | `<department>/<id>/signed/` | later of `agreement_changed_at` and `content_changed_at`, else `created_at` | `doc_type, department, company, document_number, client_name, contact_name, contact_email, contact_phone, client_address, license_number, vat_trn, services, lines, vat_mode, vat_rate, vat_amount, total_amount, valid_until, notes, field_values, library_template, library_file_id, template_key, storage_path, word_path, agreement_changed_at`. Inside `field_values` the accepted option and `file_history` do not count; for `AB Capital/Accounting Quote` and `AB Capital/Proposal` lines, services, VAT and total mirror the accepted option and do not count |
| `ardentax_documents` | `hub-documents` | `ArdentTax (ASP)/<id>/<uuid>/…` (`ardentax/services/generate.js`) | `ArdentTax (ASP)/<id>/signed/` | `content_changed_at`, else `created_at` | `doc_type, document_number, version, quote_type, client_name, selected_package, volume, one_time, annual, year1_total, details, word_path, pdf_path` |
| `banking_quotations` | `banking-documents` | `<case id>/generated/<uuid>-<name>` (`bankingApi`), listed in `banking_generated_documents` | `<case id>/generated/<id>/signed/` | later of `content_changed_at` and the newest generated file of the quotation | `quotation_number, version, case_id, recommendation_id, bank_id, scheme_id, quotation_date, valid_until, payment_terms, remarks, vat_mode, vat_rate, bank_fee_total, service_fee_total, supplementary_total, discount_total, vat_amount, total_amount, direct_to_bank_total, initial_deposit_memo, minimum_balance_memo` |
| `banking_engagement_letters` | `banking-documents` | as above | `<case id>/generated/<id>/signed/` | later of `content_changed_at` and the newest generated file of the letter | `letter_number, case_id, quotation_id, version, letter_date, content` |
| `banking_receipts` | `banking-documents` | as above (kind `receipt`, by payment) | `<case id of the payment>/generated/<id>/signed/` | later of `content_changed_at` and the newest generated file of the receipt | none: the table is append-only, so the column is only its creation stamp |

Status, mail, approval, OneDrive, client link and signing columns never move the stamp. When a content column changes value the live signature is superseded (`Document changed`). The banking tables have no `created_at`, so their `content_changed_at` defaults to the row's creation (existing rows: the time 011 ran). Every family stores its generated files server-side today, so no `<family>/<id>/signed/` fallback prefix was needed. Banking regenerates by adding a generated file, which moves the stamp but does not touch the row: its regenerate path calls `doc_sign_supersede` (allowed for any reader once the stamp has moved).
