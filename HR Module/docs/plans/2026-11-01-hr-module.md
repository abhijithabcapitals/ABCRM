# HR Module Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an HR tab to the CRM covering employees, documents, leave, attendance, payroll, and a task view on its Dashboard.

**Architecture:** A React folder (`HR Module`) imported by Main Module through an `@hr` alias, as Banking is. Rules that protect data or money live in PostgreSQL (`Database Module/HR Base`): RLS for access, `security definer` functions for decisions. It extends the existing `hr_employees` table.

**Tech Stack:** React and Vite (Main Module), Supabase, PostgreSQL 18 locally for tests, `node --test`. UI from `@banking/components/shared`.

**Spec:** `HR Module/docs/specs/2026-11-01-hr-module-design.md`

## Global Constraints

- Work in a git worktree on branch `hr-module`, cut from `ai-usage-optimize` commit `57a3ec3` or later. Another session commits to the main checkout, so do not switch branches there. Do not include its uncommitted Banking template or Template Module changes.
- Do not apply migrations to live Supabase, push, merge or deploy without the user's approval.
- Migrations are idempotent, use `public.hr_*`, and follow `Banking Base/migrations` style. Money is `numeric(18,2)` in AED, never float.
- Keep `001_hr_employees.sql` unchanged. Add later migrations only. Settings > Employees and member onboarding must keep working.
- No payroll rule value (daily-rate basis, gratuity, statutory leave days, WPS layout) is written from memory. Values come from settings or from sources recorded in `HR Base/docs/PAYROLL_RULES.md`.
- The module never sends money or submits to a bank.
- Personal test data only. No real employee data in the repo.
- UK English in user-facing text. Errors use `ErrorNote`, and entered data stays on screen.

## Review Focus

- Same-name employees: the task view shows a warning, because `tasks.assignees` holds names. Test in Task 3.
- Leave across a month or year end, and across weekends and holidays: days count correctly, and balances charge the right year. Test in Task 4.
- Employee who joins or leaves mid-month: pay is pro-rated, and the pay run does not silently pay a full month. Test in Task 7.
- Employee with status `Left`: expired documents no longer raise alerts. Test in Task 2.
- Attendance or leave edited after review but before approval: approval is refused and lists the changed employees, rather than locking stale figures. Test in Task 7.
